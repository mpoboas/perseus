# Perseus threat model

A structured self-review, written for contributors and for whoever eventually commissions an
external review. It is not a substitute for one.

## What is protected

| Asset | Where it lives |
|---|---|
| Git host tokens (PAT, OAuth access/refresh) | OS keychain (`keyring`), looked up by the credential helper or Rust code; never sent to the webview |
| SSH private keys | Files on disk (the user's, or generated by Perseus in the app data folder); only the path is stored in a profile |
| Passwords / passphrases typed in a prompt | In memory only: webview → Rust → the waiting git/ssh process |
| Source code and history | The user's repositories |
| Identity (name, e-mail, signing key id) | Profile store (JSON in the app data folder) |

## Actors and trust

- **The user**: trusted.
- **The webview (our own frontend)**: *not trusted with secrets or the filesystem.* A bug (XSS in a
  commit message, a malicious dependency) must not become code execution or credential theft.
- **Repository contents** (file names, branch names, config, hooks, `.gitattributes`, commit
  messages): untrusted. Cloning a hostile repository must not run code on open.
- **Git hosts and OAuth providers**: trusted for what they are, but their responses are validated;
  rate limiting and ETags are respected.
- **Other local processes**: only the loopback askpass server is reachable (see below).

## Entry points and mitigations

| Threat | Mitigation |
|---|---|
| Webview calls a command it should not | Tauri capabilities list only app commands; the Isolation pattern's hook allows only the same list; a test (`isolation_allowlist`) fails when `build.rs`, `capabilities` and `isolation/index.js` disagree |
| Webview reads files or runs programs | No `fs`, `shell`, `opener` or `dialog` grants; pickers are opened from Rust; frozen prototype; strict CSP (`script-src 'self'`, `style-src 'self'`, `object-src 'none'`, `frame-ancestors 'none'`) |
| Argument injection through branch/tag/ref/path names (`-x`, `--upload-pack=…`, `;`, `$()`) | Arguments are always a vector (never a shell); every webview string passes `git/validate.rs` (refs through gix's rules, leading `-` refused, paths relative without traversal); `--` separators; `GIT_LITERAL_PATHSPECS=1` |
| Repository config that runs programs (`core.fsmonitor`, `diff.external`, textconv, `core.sshCommand`, hooks on open) | Read paths use gix (no execution); the CLI runs with `--no-ext-diff --no-textconv`, a scrubbed environment and no repo-chosen helpers for read-only commands. Hooks run only when the user commits/pushes and can be skipped explicitly |
| Credential-protocol injection (CVE-2020-5260 class: newline in a URL/host) | `perseus_credentials::validate` rejects `\n`, `\r` and NUL in every field; unit tests cover it |
| Token exposure in logs, argv, errors, the activity log | Tokens are passed through the credential helper/environment of the child, never argv; URLs are redacted (`://user:pass@` → `://***@`) before logging; no token is ever returned to the webview; tests check redaction |
| Local process abusing the askpass server | Listens on loopback only, requires a random per-session token (passed to children by environment), answers only for the running session, 15-minute wait, answers delivered to exactly the waiting child |
| Hostile prompt text (spoofed "Password for github.com") | The dialog shows git's own prompt text verbatim in a monospaced box; "trust this host" shows the fingerprint and recommends comparing with the provider's published one |
| Hostile OAuth redirect / CSRF | Device flow for GitHub and GitLab: no redirect URI and no local web server, so there is nothing to forge; the user approves a code on the provider's own page |
| Hostile file content in the diff/blame/conflict views | Rendered as text through React (no `dangerouslySetInnerHTML`), size-capped and virtualized |
| Patch apply / submodule / worktree paths escaping the repository | Patches are applied by `git apply`, which refuses paths outside the work tree; `open_nested_repo` accepts only paths the repository itself reports as submodules or worktrees; worktree names and refs validated |
| Supply chain | `cargo deny` (advisories, licenses, sources) and `pnpm audit` in CI and weekly; every ignored advisory documents a reason; lockfiles committed |
| Profile pictures as a tracking or SSRF channel | Pictures come from GitHub (`avatars.rs`): URLs are assembled in Rust from a validated account id or login, a validated `owner/repo` and commit id (GitHub's commit record), or the signed-in account, never from webview input; picture hosts in responses are checked against `avatars.githubusercontent.com`; Gravatar is an explicit opt-in because it sends an address hash to a third party; downloads are size-capped, must be images, and reach the webview only as `data:` URLs, so the CSP gains no remote image source. A preference turns it off |
| Undo and redo moving the wrong refs | `git/undo.rs` only touches local branches and HEAD, validates every name and commit id, refuses while a merge, rebase, cherry-pick or revert is in progress, uses `reset --keep` so uncommitted work is never overwritten, and has tests with real repositories |
| Destructive operations by accident | A confirmation step with an explanation for anything that rewrites history or discards work; force push uses `--force-with-lease`; cancellation kills the whole process tree |

## Known residual risks

- **Hooks and `.git/config` in the repository are Git's normal trust model.** Committing,
  pushing or rebasing runs the repository's hooks; Perseus does not sandbox them. Opening or
  browsing a repository does not run them.
- **SSH host trust** relies on the user comparing a fingerprint.
- **Unsigned installers** until the owner supplies certificates; SmartScreen/Gatekeeper warnings
  are expected until then. There is no auto-update yet, so no update channel to attack.
- **No external audit** has taken place.
- **macOS and Linux** keychain/askpass behaviour is untested (Secret Service may be absent).
- **GPG signing** is not supported; only SSH signing is.
- The loopback askpass port is reachable by other processes of the same user; the token is the only barrier.

## Reviewing a change

Ask for every change: does a new string reach git without `validate.rs`? does a new command appear
in all three places? can a secret reach the webview, a log, argv or an error message? does a new
dependency pass `cargo deny`? does it need a CSP change (test it in a release build)?
